# EXP-DSA05-010 第 0 阶段：工程与验收

## 1. 结论

1. **设计 §5 的实现都已完成，全部测试通过**：

   - EXP-006、008、009 的测试与冻结守护测试都没有改动，仍然通过；

4. **训练池上的健全性检查**（N = 8，种子 101，按设计数据量的 1/3，3 次迭代，非正式）：
   - 学生执行时与老师动作的一致率从 0.31（第 2 次迭代）升到 0.63（第 3 次）；
   - 学生执行的 rollout 中，包违约率从 1.2% 降到 0.18%。
   - 损失随迭代下降，没有发散，可以进入正式运行。这些是训练侧的数，不是评估结果。
5. **估计耗时**：
   - 每个运行约 45–60 分钟，峰值内存约 2–2.5 GB；
   - 6 个运行并行约 1–1.5 小时；
   - 筛选（36 个检查点 × 256 个回合）约 1 小时；
   - 判别评估（30 个块 × 512 个回合）约 2 小时；
   - 全程约 4–5 小时。

## 3. 设计未写明的实现决定

1. **"一致率"**：学生按自己的分布采样的动作与老师在同一状态下的动作相同的比例，只统计有包的 UE 时隙。训练日志与 `diagnose_exp010.py` 用同一口径。
2. **碰撞比例**：发送的 UE 时隙中，与至少一个其他 UE 同用一个子信道的比例。
3. **第 1 次迭代由老师执行**：每个环境、每个时隙执行的就是老师的联合动作（测试逐个核对了执行的动作等于标签）；学生在这一次迭代中同样运行它的 GRU，但它的动作只用于统计一致率。
4. **按回合训练**：14 个环境的回合同时开始、同时结束（600 时隙），每个回合作为一个数据单元；一个 mini-batch 是 16 个回合并排，按段依次处理，每段一次优化步。
5. **A_mix 与 M 的模型**直接取自已冻结的 EXP-009 方法清单（`docs/results/exp009-confirm_methods/methods-v2-confirm2.json`）中 N = 6、8、10 的种子层，不重新选择。

## 4. 冒烟检查（非正式，不作为结果）

`diagnose_exp010.py` 在开发实例 1,000–1,003 上运行，学生用上述健全性检查的第 3 次迭代检查点：
- 学生与 EDF 的动作一致率约 0.54–0.60，A_mix 与 M 约 0.40–0.48；
- 学生的碰撞比例约 0.23–0.40，A_mix 与 M 约 0.11–0.22。

这只用于确认脚本能跑通。它正好呈现了设计 §4 预见的风险：模仿老师的"何时、用哪个信道发"，但没有协调，导致碰撞增加。正式结论以 exp010-eval512 上的 F 为准。
